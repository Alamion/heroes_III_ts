# Updating Heroes 3 Living Map on Steam Workshop from GitHub Actions

## 1. Is there a supported unattended uploader for Wallpaper Engine?

### Takeaway

As checked on **2026-11-27**, the Wallpaper Engine editor is the only confirmed publishing path for item **3808342201** (app **431960**). SteamCMD can update Workshop items for some other apps; I found neither a documented blanket SteamCMD ban specifically for Wallpaper Engine Web items nor a reproducible successful `workshop_build_item` update for app 431960. Its suitability is an open question, not a supported feature to build CI around.

### Cited Findings

- The [live item](https://steamcommunity.com/sharedfiles/filedetails/?id=3808342201) identifies **Alamion** as the creator and shows `Type: Web`, `Age Rating: Everyone`, `Genre: Game`, `Miscellaneous: Customizable`, and `Category: Wallpaper`. The raw HTML contains hidden `bannedNotification` and `incompatibleNotification` elements (`display: none`); text-only scrapers surface these boilerplate banners, so their presence is not evidence of a ban. The [public Change Notes](https://steamcommunity.com/sharedfiles/filedetails/changelog/3808342201) show three entries, most recently October 1, beginning with `0.1.4`; the [latest GitHub release](https://api.github.com/repos/Alamion/heroes_III_ts/releases/latest) was `v0.2.0` at read time. This establishes a visible change-note lag, not byte-for-byte knowledge of the current Steam install.
- The [Wallpaper Engine publishing guide](https://docs.wallpaperengine.io/en/scene/first/publishing.html#publishing-updates) documents publishing updates through the editor. The [repo procedure](https://github.com/Alamion/heroes_III_ts/blob/testing/docs/releasing.md#4-update-the-steam-workshop-item) uses Windows, the item's owner logged into Steam, and the `workshopid` in the local project manifest. The [official CLI](https://help.wallpaperengine.io/en/functionality/cli.html#command-overview) targets a running Wallpaper Engine process; its `openWallpaper` applies/previews a wallpaper. It documents playback, wallpaper/playlist/profile selection, settings, icons, and querying the current wallpaper; no publish/update, editor upload, or change-note operation is listed. [Wallpaper Engine Steamworks support](https://help.wallpaperengine.io/en/steam/steamworks.html) explicitly says to use the account which owns Wallpaper Engine and avoid mismatched/elevated processes. Wallpaper Engine itself is [Windows-only per its support site](https://help.wallpaperengine.io/en/functionality/linuxmacos.html).
- Valve documents `workshop_build_item` [under SteamCmd Integration](https://partner.steamgames.com/doc/features/workshop/implementation#SteamCmd) as a **testing** route, explaining that it requires entering Steam credentials. The VDF for an update must include the target App ID and a nonzero existing `publishedfileid`; only provide the remaining fields that should be changed. The same [implementation guide](https://partner.steamgames.com/doc/features/workshop/implementation) documents per-app Steam Cloud quota and an **Enable ISteamUGC for file transfer** flag, plus **App Publish Permissions** when a *different Steam App ID* is used as the publishing tool. These publisher settings cannot be changed by a Workshop item owner. Public [431960 AppInfo mirror](https://api.steamcmd.net/v1/info/431960) shows `depots.workshopdepot=431960` and a nonzero UFS quota (`33554432`, 100 files); this is consistent with a modern Workshop depot, but reveals no server-side permission for SteamCMD or an independent client. By comparison, [Tabletop Simulator AppInfo](https://api.steamcmd.net/v1/info/286160) has no `workshopdepot`, and a [Tabletop Simulator community experiment](https://www.reddit.com/r/tabletopsimulator/comments/v5t9sw/uploading_to_steam_workshop_as_part_of_cicd/) reports a legacy-format failure; that is evidence about a different app, not 431960.
- Real, documented Wallpaper Engine restriction: the developer's [2.8.42 announcement](https://store.steampowered.com/news/app/431960/view/699894448411116924) removed Workshop upload/download for **Application** (executable) wallpapers. The [official Steam news feed](https://api.steampowered.com/ISteamNews/GetNewsForApp/v2/?appid=431960&count=15&maxlength=0) has the full announcement. The project publishes a **Web** wallpaper; neither the announcement nor the 431960 forum searches for [`steamcmd`](https://steamcommunity.com/app/431960/discussions/search/?q=steamcmd) and [`workshop_build_item`](https://steamcommunity.com/app/431960/discussions/search/?q=workshop_build_item) establishes a general rule specifically permitting or prohibiting SteamCMD updates of Web items. Reports on SteamCMD downloading or installing Wallpaper Engine do not establish upload support.

### Inferences

- Use the existing owning account (and its Wallpaper Engine license) as the acceptance baseline. A fresh bot account buying 431960, a visible co-author/contributor credit, GitHub ownership, an anonymous SteamCMD session, or merely adding `workshopid` to `project.json` does not establish update rights. Do not assume contributors can update, or that Steamworks build-account permissions for depots confer rights to a user item. The package's `workshopid` tells the editor which item to target; it is not authorization. [Repo procedure](https://github.com/Alamion/heroes_III_ts/blob/testing/docs/releasing.md#4-update-the-steam-workshop-item) · [Valve Workshop guide](https://partner.steamgames.com/doc/features/workshop/implementation) · [Valve SteamPipe build accounts](https://partner.steamgames.com/doc/sdk/uploading#Build_Account).

### Gaps

- No app-specific permission decision, sanctioned publisher CLI, documented working headless tool, or end-to-end authenticated upload test for 431960 was found. No account was signed into, and no upload (including private) was attempted. A refusal from the server could reflect account, entitlement, app configuration, agreement, or content policy; a generic `AccessDenied` alone does not identify which. A later authorized test should use a **separate private test Web item** created via the ordinary editor and ask the vendor first whether a direct client is supported. Do not try to work around a publisher/access restriction or test on the live item.

## 2. What do existing SteamCMD, Steamworks and SteamKit tools actually prove?

### Takeaway

SteamCMD wrappers prove generic hosted Workshop automation, not Wallpaper Engine compatibility. Direct Steamworks CLI tools use the running licensed Steam client's user session: they are credible local experiments after vendor confirmation, not drop-in hosted CI. SteamKit is a lower-level network library, not a confirmed Workshop file uploader for this app.

### Cited Findings

| Tool | Mechanism and strength of evidence |
| --- | --- |
| **BUTR/Bannerlord.SteamWorkshop**, SteamCMD | An actual [Bannerlord UIExtenderEx workflow](https://github.com/BUTR/Bannerlord.UIExtenderEx/blob/9a6f063ec9f8924feb51294ff0056501efc863c5/.github/workflows/publish.yml) names the [real Workshop item 2859222409](https://steamcommunity.com/sharedfiles/filedetails/?id=2859222409), and the [reusable workflow](https://github.com/BUTR/workflows/blob/master/.github/workflows/release-steam.yml) installs SteamCMD then calls `loginandpublish`, which invokes [`workshop_build_item` in source](https://github.com/BUTR/Bannerlord.SteamWorkshop/blob/master/src/Bannerlord.SteamWorkshop/Program.cs). The tool is for Bannerlord; its separate `steamretag` operation needs the desktop client. This ties a real pipeline to an item on another app, without inferring that every run succeeded or that it works for 431960. |
| **m00nl1ght-dev/steam-workshop-deploy**, SteamCMD | Inspected [v4 source at `7abf9c7628c3bc79229c9bca93f7a7296fa82428`](https://github.com/m00nl1ght-dev/steam-workshop-deploy/blob/7abf9c7628c3bc79229c9bca93f7a7296fa82428/steam_deploy.sh). A Linux Docker Action stages files and passes `appid`, `publishedfileid`, content directory and change note to SteamCMD. [GHSA-x6gv-2rvh-qmp6](https://github.com/BoldestDungeon/steam-workshop-deploy/security/advisories/GHSA-x6gv-2rvh-qmp6) documents a real `.git` exposure before v4 (including potential checkout credentials); [Marketplace examples](https://github.com/marketplace/actions/steam-workshop-deploy) still show the affected `@v3`. The v4 shell writes `config.vdf` with mode `777`, logs SteamCMD files on error, interpolates the change note into a VDF without escaping, and its rsync staging is not automatically cleaned. Do not pass raw generated BBCode through that template without checking VDF encoding/quoting, or use shared staging. No 431960 evidence. |
| **Other hosted Actions** | [hmlendea/steam-workshop-update](https://github.com/hmlendea/steam-workshop-update) wraps native SteamCMD for existing-item updates and optional TOTP; it explicitly trusts SteamCMD's exit status and notes the need for an external timeout. [RageAgainstThePixel/upload-steam](https://github.com/RageAgainstThePixel/upload-steam) supports a Workshop mode and documents mobile approval on first login plus intermittent reapproval of cached sessions; its examples assume Steamworks build access. [game-ci/steam-deploy](https://github.com/game-ci/steam-deploy) is a SteamPipe **game/depot** deployer, not a Workshop content uploader. None establishes Wallpaper Engine support. |
| **SimKDT/Steam-Uploader**, native Steamworks | [README](https://github.com/SimKDT/Steam-Uploader) reports actual Windows 10/11 and Linux Mint testing; shows Project Zomboid usage and an existing-ID update with optional patch-note file. [Source](https://github.com/SimKDT/Steam-Uploader/blob/main/src/Uploader.cpp) calls `SteamAPI_Init`, `StartItemUpdate`, `SetItemContent` and `SubmitItemUpdate`, runs callbacks, and has a separate create path. Stated platform tests are not 431960 tests. Audit the setter/return handling and confirm actual finished upload before considering it for a worker. |
| **gibbo101/steam-workshop-uploader** (Steamworks.NET) and **ewolf-studio/steam-workshop-cli** (Facepunch.Steamworks) | [Gibbo source](https://github.com/gibbo101/steam-workshop-uploader/blob/main/Program.cs) is a Linux-native example which requires a logged-in owner, unconditionally sets visibility and can create on a missing ID. Its [README](https://github.com/gibbo101/steam-workshop-uploader) reports stale-session hangs in the author's use case, not a universal restart requirement. [Ewolf README](https://github.com/ewolf-studio/steam-workshop-cli) names a RimWorld release pipeline and supports Windows/Linux, JSON, a manifest-only dry-run and an explicit `--create` switch. Its illustrative [RimWorld Workshop item](https://steamcommunity.com/sharedfiles/filedetails/?id=3733416045) exists. Both are real implementations, neither demonstrates an upload to 431960; multi-language/multi-submit flows and setters for title, visibility, or tags are unnecessary risk for an ordinary update of this item. |
| **SteamKit2**, network protocol | [SteamRE/SteamKit](https://github.com/SteamRE/SteamKit) exposes network services and [shows bearer/refresh-token authentication](https://github.com/SteamRE/SteamKit/blob/master/Samples/000_Authentication/Program.cs). [PublishedFile protobuf definitions](https://github.com/SteamDatabase/Protobufs/blob/master/steam/steammessages_publishedfile.steamclient.proto) include `Publish`/`Update`. Neither a generated RPC nor a login sample demonstrates end-to-end content upload plus preview, item permission and app compatibility. Valve's documented [PublishedFile Web API](https://partner.steamgames.com/doc/webapi/IPublishedFileService) exposes queries and some publisher-key operations, not a documented public Workshop content upload endpoint for the item's owner. No usable SteamKit tool was found for this job. |

- [Valve's Steam API init docs](https://partner.steamgames.com/doc/api/steam_api#SteamAPI_Init) require a running client, its same OS user/privilege context, an identified App ID, and an active account holding that App ID's license. `steam_appid.txt` supplies app context for direct/during-development launches; it grants no entitlement or publishing rights. [Steamworks.NET](https://github.com/rlabrecque/Steamworks.NET) is a C# binding to the same API; native wrapper availability on Linux does not establish a supported Wallpaper Engine editor or supported external uploader. A separate publisher App ID needs the [Steamworks app-permission arrangement](https://partner.steamgames.com/doc/features/workshop/implementation#FAQ).
- For any authorized direct Steamworks test, the operation under evaluation would be **existing-item update only**: `StartItemUpdate(431960, testItemId)` → stage just `SetItemContent` → `SubmitItemUpdate` with change note. Check handle, setter result, I/O status, callback `EResult`, expected item ID, and legal-agreement flag; observe progress and verify downloaded content in a real Wallpaper Engine client. Do not set title, description, preview, visibility, tags or metadata unless a deliberate, separately verified change. Valve says submission cannot be cancelled; a timeout can have an unknown outcome. [ISteamUGC API](https://partner.steamgames.com/doc/api/ISteamUGC) · [Workshop guide: uploads, legal agreement and logs](https://partner.steamgames.com/doc/features/workshop/implementation).
- A GitHub-hosted `[windows|ubuntu]-latest` job gets a fresh runner, not Alamion's logged-in Steam client. SteamCMD Actions can log in some accounts using password plus Steam Guard code derived from a persistent `shared_secret`, a cached SteamCMD `config.vdf` containing session credentials, or phone approval and renewal. These solve **authentication only**; none establishes authorization for 431960. Cached session credentials remain sensitive, can stop working or require reapproval, and have no demonstrated durability here; storing a password and TOTP seed together hands both factors to the deploy job. Prefer keeping the owner account and session entirely local, including cookies/refresh tokens; no Steam credentials in logs, bundles, Actions caches, or artifacts. [GitHub-hosted runners](https://docs.github.com/en/actions/concepts/runners/github-hosted-runners) · [v4 authentication contract](https://github.com/m00nl1ght-dev/steam-workshop-deploy#configuration) · [mobile approval/caching example](https://github.com/RageAgainstThePixel/upload-steam#multi-factor-authentication-setup).

### Gaps

- Generic uploader discovery establishes real mechanisms and some other-app adoption. Neither a successful generic tool process nor a logged-in client alone establishes permission, correct Wallpaper Engine tags/age classification, compatibility/visibility, or working subscriber installation for this app. No stable, per-item-scoped credential for an unattended hosted uploader was identified.

## 3. What should this repo automate now?

### Takeaway

Keep Linux Actions as the release builder. Have the owner's Windows desktop fetch and stage a verified final release, and leave the actual **Publish update** confirmation in Wallpaper Engine. This gives near-one-click publishing without handing the public repo a Steam session. Treat a local direct-SteamUGC uploader as a separate research experiment, with an editor fallback.

### Cited Findings

- Current [release workflow](https://github.com/Alamion/heroes_III_ts/blob/testing/.github/workflows/release.yml) starts from `v*`/`workflow_dispatch`, requires check, hosts and build before the `release` job, and uses `github.token`. [`publish.ts`](https://github.com/Alamion/heroes_III_ts/blob/testing/tools/release/publish.ts) can create the release before assets are attached, or fill an existing manually created release; attachments use `--clobber`. GitHub documents that `GITHUB_TOKEN`-originated release actions do **not** trigger a separate `on: release` workflow; explicit `workflow_dispatch`/`repository_dispatch` can trigger a run. [`workflow_run: completed`](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run) is another option (must be on the default branch; require the successful `release` workflow and validate tag/artifact provenance before crossing a privilege boundary). [GitHub recursion rule](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#triggering-a-workflow-from-a-workflow).
- Read-only check of the [v0.2.0 ZIP](https://github.com/Alamion/heroes_III_ts/releases/download/v0.2.0/heroes3-living-map-wallpaper-engine-0.2.0.zip) and [SHA256SUMS](https://github.com/Alamion/heroes_III_ts/releases/download/v0.2.0/SHA256SUMS): SHA-256 `95f92bf6639b26816d41a39bd8d01904b320a04491beb8a1b55445b1b1a587c6` agrees with the release asset digest. ZIP has exactly `README.txt`, `index.html`, `listener.js`, `main.js`, `page.css`, `preview.png`, `project.json`; manifest gives `file: index.html`, `type: web`, `contentrating: Everyone`, `workshopid: "3808342201"`. GitHub's [asset API](https://docs.github.com/en/rest/releases/assets?apiVersion=2022-11-28#get-a-release-asset) allows unauthenticated reads of public assets and returns a digest. The repo's [constitution I](https://github.com/Alamion/heroes_III_ts/blob/testing/.specify/memory/constitution.md#i-user-supplied-assets-only-non-negotiable) and [release docs](https://github.com/Alamion/heroes_III_ts/blob/testing/docs/releasing.md#4-update-the-steam-workshop-item) forbid user-supplied game files in the upload directory; the editor uploads the folder.
- GitHub [advises against self-hosted runners for public repos](https://docs.github.com/en/actions/reference/security/secure-use#hardening-for-self-hosted-runners) because untrusted workflows can persistently compromise them. A Windows Scheduled Task with [interactive-token logon](https://learn.microsoft.com/en-us/windows/win32/taskschd/principal-logontype) runs only in an existing logged-on session. This aligns with Wallpaper Engine/Steamworks' live-client requirements, while keeping the personal session outside a general-purpose runner. [Wallpaper Engine Steamworks help](https://help.wallpaperengine.io/en/steam/steamworks.html) · [Steam API init](https://partner.steamgames.com/doc/api/steam_api#SteamAPI_Init).

### Inferences

1. **Preferred trigger: desktop pull.** An allowlisted desktop helper polls the public Releases API at login or on a schedule (or is run via a shortcut for a specific tag). A plain tag push or `release.published` signal is only a hint: a maintainer can create a release early and CI currently uploads its files separately. Wait for non-draft, non-prerelease `vX.Y.Z`, expected checksummed ZIP and matching change-note asset in `uploaded` state, and the relevant successful release workflow or an explicit handoff emitted after the `release` job. If a push signal is needed, append a dependent job or consume verified `workflow_run: completed`; a webhook listener can verify signatures and schedule the same local pull. There is no need for an inbound endpoint on the desktop or a Steam token in GitHub. [Repo workflow](https://github.com/Alamion/heroes_III_ts/blob/testing/.github/workflows/release.yml) · [GitHub webhook validation](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries).
2. **Stage against explicit inputs.** Pin repo, app ID and item ID; validate the tag, its commit, release identity, expected asset names/digests, and change-note contents. Verify ZIP and note against `SHA256SUMS`, preferably also against the expected digest from a trusted completed run. Checksums served alongside mutable assets detect corruption and mismatches, not a compromised source. Use an owner-installed fixed helper, not code downloaded and executed from a release. Extract into a fresh dedicated staging directory; reject traversal, absolute paths, symlinks/reparse points, unexpected members, nested archives and game data, and validate root `project.json`. Use a clean dedicated editor project with a backup and no game files or stale payload; do not unzip over a development/test profile containing `.lod`, `.h3m`, `game/maps.zip`, caches, or captures. Keep `changenote-*.bbcode` outside the uploaded tree. Immutable releases and attestations could strengthen provenance, but [GitHub's immutable-release workflow](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases) requires filling a draft before publication and is incompatible with the current `--clobber` rerun without a design change.
3. **One-click preparation / manual final commit.** Shortcut stages the verified folder, makes the change note ready to paste and opens the release/project location. The owner opens it in the editor (if already open, refresh/reopen after staging), chooses **Workshop → Share Wallpaper on Workshop → Publish update**, verifies item ID and **Everyone** / existing visibility, pastes the note and confirms. The documented CLI `openWallpaper` can preview; it does not open the publishing dialog. Without a helper the existing `docs/releasing.md` flow remains usable. Title/description/gallery stay conditional/manual; use a separate test copy to supply game assets. Full desktop click automation would depend on UI version, foreground session, locale and unexpected dialogs; if tried, restrict it to preparing the screen for an owner confirmation rather than clicking through auth, new-item prompts or the final action. [Editor guide](https://docs.wallpaperengine.io/en/scene/first/publishing.html#publishing-updates) · [Repo release guide](https://github.com/Alamion/heroes_III_ts/blob/testing/docs/releasing.md#4-update-the-steam-workshop-item).
4. **Handling failure and replay.** Lock per item across versions; remember release tag, commit and asset digest with separate `staged`/`published` states. Identical reruns do not republish; a changed digest for a processed tag or a downgrade requires explicit review. Stop on changed item/owner/license, wrong age rating/type, missing files/digest mismatch, editor offering **Publish** instead of **Publish update**, Steam Guard/terms prompt, or timeout with unknown outcome. On timeout inspect Workshop Change Notes, Steam logs and actual subscriber install before retrying; don't blindly append duplicate updates. Successful editor/API submission can precede propagation: verify the **same public item** plus intended note and a clean subscriber installation in Wallpaper Engine, with expected Web classification/tags and visibility. Record confirmation locally. Recovery is a separately approved re-publish of the preceding verified package under the same ID, rather than deletion/recreation. [Valve upload and diagnostics](https://partner.steamgames.com/doc/features/workshop/implementation) · [Wallpaper Engine update propagation](https://docs.wallpaperengine.io/en/scene/first/publishing.html#publishing-updates).
5. **If a runner or direct publisher is later approved:** use a dedicated restricted worker/VM and an interactive user context when needed; avoid registering the owner's Steam desktop as a runner for the public repository. Prefer a read-only artifact consumer over arbitrary jobs, or an isolated private dispatch workflow with owner approval, protected/tag-allowlisted inputs, minimized token scope, pinned dependencies, and no PR-controlled code or ambient owner session. Keep Linux package generation and verification as shared tooling; any Windows desktop procedure is a host-specific handoff. [GitHub secure use](https://docs.github.com/en/actions/reference/security/secure-use) · [Project constitution V](https://github.com/Alamion/heroes_III_ts/blob/testing/.specify/memory/constitution.md#v-platform-agnostic-core-linux-first-development).

### Gaps

- No desktop helper, VDF upload, direct client update, approval mechanism, or service was run or implemented. The read-only artifact and changelog checks support the handoff design; they do not certify any unattended publisher or the public item's current payload.
