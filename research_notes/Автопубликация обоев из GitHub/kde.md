# KDE Store / Pling publishing for Heroes 3 Living Map (2374098)

Research checked **2026-11-27** via public reads only. No login, write endpoint, product change, or anti-bot challenge was attempted.

## 1. Is there an official API for publishing a release?

### Takeaway

There is a working public OCS API for reading the store product; no supported, production-ready KDE Store publishing API was verified. The OCS standard does describe writes, and a contemporary report says OpenDesktop is planning a documented publishing API, so “OCS is read-only” is too broad.

### Cited Findings

- KDE's [provider configuration](https://autoconfig.kde.org/ocs/providers.xml) advertises `https://api.kde-look.org/ocs/v1/` and the OCS 1.6 person/content services. On 2026-11-27, the [product data endpoint](https://api.kde-look.org/ocs/v1/content/data/2374098) returned OCS status `100`, name `Heroes 3 Living Map`, owner `Alamion`, category `715`, product `version=0.1.4`, `changed=2026-10-01T17:37:45+00:00`, and one Pling-hosted `heroes3-living-map-kde-0.1.4.tar.gz` with `download_version1=0.1.4`. The OCS `changelog` element was empty; that does not establish whether the store's separate changelog feed has entries. The [GitHub Releases API](https://api.github.com/repos/Alamion/heroes_III_ts/releases/latest) returned `v0.2.0` (published 2026-10-28) with its KDE archive, KDE changelog BBCode and `SHA256SUMS`. The store is already behind.
- The [freedesktop.org OCS 1.6 specification](https://www.freedesktop.org/wiki/Specifications/open-collaboration-services/#content) describes GET product and download lookup; POST `content/add`, `content/edit/<id>` (including product `version`, `changelog` and downloadable external URLs), and `content/uploaddownload/<id>` (`localfile`). It describes username/password or a provider-issued API key in general and explicitly permits services to implement only some operations. A provider advertising `content` therefore does not promise authoring operations or a way to issue product-scoped tokens.
- In [KDE Phabricator T10181](https://phabricator.kde.org/T10181) (opened 2018-12-13, author discussion through 2021), `starbuck` said upload through Get Hot New Stuff was not supported due to automated spam/upload bots. The issue is specifically about programmatic updating and distinguishes it from upload via the web UI.
- In the [KDE Discuss publishing API proposal](https://discuss.kde.org/t/proposal-official-ci-cd-publishing-workflow-for-kde-store-opendesktop/50377) (2026-09-22), the KVitals maintainer reported using manual edits. On 2026-10-19 they reported, secondhand after contacting OpenDesktop, that a documented API was planned. Product-scoped upload-only tokens were requested in the thread; no release, documentation, token provisioning, or timeline was announced there as of the research date. The [2025-12-19 discussion](https://discuss.kde.org/t/how-to-automate-downloads-from-the-kde-store/42744) points to OCS for consumption, with tools such as Apdatifier and `plasmoid-updater`; these are consumer update tools, not author-side deployment.
- The [product web page](https://store.kde.org/p/2374098/) returned an Anubis challenge (`v1.28.2`) to the research client's request on 2026-11-27. The published repository procedure is the owner's normal **Edit product → Files / Version / Changelog → Save** ([`docs/releasing.md`](../../docs/releasing.md#5-update-the-kde-store-product); [September 2026 findings](../../specs/006-release-publishing/research.md#kde-store)).

### Inferences

- Use public OCS as the machine-readable post-release check. Treat `version`, `changed`, `download_versionN` and `downloadnameN` as separate observations. Parse the OCS status as well as the HTTP status, allow for caching, and avoid retaining signed Pling download links in reports. An empty OCS `changelog` is insufficient to fail a verified web-feed edit.
- Ask OpenDesktop for the current supported write surface and acceptable automation policy before authoring an integration: existing product vs new product, archive/link handling, **product-level** version and date, changelog, product-scoped credentials, staging, rate limits, retry/idempotency and supported runner origins. `GITHUB_TOKEN` authenticates GitHub only; the spec's historical authentication examples do not establish a KDE Store credential.

### Gaps

- No provider-confirmed production write endpoint, author token scope/expiry/rotation, GitHub OIDC integration, sandbox or SLA found. No write tests were performed; the evidence supports “not verified or documented as supported,” not “every possible POST is disabled.”

## 2. Can a stable external download avoid stale releases?

### Takeaway

A stable direct archive URL could keep **new downloads** current without a KDE Store credential after a one-time edit, if today's **Files** UI and Plasma accept it. It cannot itself advance the store version, changelog, or installed users' update status.

### Cited Findings

- The OpenDesktop team [announced direct GitHub-hosted files](https://blog.opendesktop.org/github-file-links/) on 2017-02-12: links appeared in the File Download section and were counted normally. The [OCS 1.6 specification](https://www.freedesktop.org/wiki/Specifications/open-collaboration-services/#content) distinguishes an uploaded file, an external download link and a repository package. A read of [current category 715 entries](https://api.kde-look.org/ocs/v1/content/data?categories=715&pagesize=50&sortmode=new) on 2026-11-27 showed Pling hosts for the returned download URLs, not a known live GitHub example. That sample cannot distinguish local storage from all possible proxy/redirect forms.
- [GitHub documents](https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases) `/releases/latest/download/<asset-name>` for a stable manually uploaded asset name. On 2026-11-27, the [versioned 0.2.0 archive](https://github.com/Alamion/heroes_III_ts/releases/download/v0.2.0/heroes3-living-map-kde-0.2.0.tar.gz) redirected to GitHub's release asset host and returned `200`, `application/octet-stream`, and the archive filename in `Content-Disposition`. The [proposed stable alias](https://github.com/Alamion/heroes_III_ts/releases/latest/download/heroes3-living-map-kde.tar.gz) returned `404`; there is no such unversioned asset in the latest release. `/releases/latest` alone is an HTML page. GitHub's [latest release API documentation](https://docs.github.com/en/rest/releases/releases#get-the-latest-release) excludes drafts and prereleases; this repository's [workflow](https://github.com/Alamion/heroes_III_ts/blob/testing/.github/workflows/release.yml) gates Pages on a final release, and [`tools/release/publish.ts`](../../tools/release/publish.ts) currently creates/edits the release before uploading assets.
- [KNewStuff's Attica requester](https://github.com/KDE/knewstuff/blob/master/src/attica/atticarequester.cpp) (checked 2026-11-27) sets the entry version from OCS `content.version()` and its release date from `content.updated().date()`. An installed entry becomes `Updateable` when **either differs** from the cache; this is a date comparison, not full timestamp or SemVer ordering. The individual download's version is read separately. [Attica provider code](https://github.com/KDE/knewstuff/blob/master/src/attica/atticaprovider.cpp) obtains the actual payload URL from the OCS download lookup. A new version inside the archive, or a redirect changing its target without a store edit, does not enter the update decision.

### Inferences

- Preferred link candidate: publish an additional `heroes3-living-map-kde.tar.gz` containing the exact checked final archive under the documented GitHub latest URL, keeping the versioned release artifact. Verify the alias is public and byte-identical before using it. A moving “latest” release that is made public before asset upload can briefly return `404` (including while replacing an alias on rerun); stage assets before changing the public pointer, or use an owned HTTPS redirect committed only after download and checksum validation. A separate redirect can point to the immutable tagged asset and roll back independently; GitHub Pages HTML or JavaScript redirects are not a substitute for a server-side redirect yielding archive bytes to Plasma. Fail closed if the link cannot deliver the expected bytes.
- First authorized trial: check the owner's **Files** editor for an actual **downloadable external link** option (a source/homepage link does not count); on a separate test listing in the same category, if permitted, add the already-existing tagged URL first. Verify store Files plus OCS lookup, follow the payload redirects, compare the final archive to `SHA256SUMS`, and clean-install via Plasma 6 **Get New Plugins…**. Then test the stable URL through a target change: check Store/OCS filenames, checksum/payload and Plasma while metadata is unchanged, then explicitly bump product Version and confirm an existing install is offered an upgrade. Keep the hosted production file until the install and upgrade paths are verified; if links are unsupported, keep manual hosting.
- Even if the trial passes, continue updating product Version and changelog per final release. Treat the stable link as a way to eliminate upload handling and stale **new-install bytes**, with a visible risk of old product metadata alongside newer bytes until the owner saves. If matching metadata and bytes at all times matters more, use an immutable versioned link updated with the store metadata or stay with the hosted file.

### Gaps

- Current owner UI field availability under category 715, accepted host allowlists, redirects and expiry handling, whether Pling mirrors/caches the archive or pins any checksum at creation, download credit, and actual Plasma install/upgrade across a moving link remain untested. The 2017 announcement is historical support for direct GitHub files; it is not a current contract for a custom redirect or mutable URL.

## 3. What can Actions do now, and when is browser automation worth it?

### Takeaway

Add an Actions readback/reminder and keep the owner finishing the store update. A public GitHub-hosted Actions example really did upload to Pling in November 2026, but it uses reverse-engineered web calls, account credentials, destructive replacement, and does **not** set the product-level version. It is evidence of technical feasibility, not a safe drop-in for this wallpaper.

### Cited Findings

- The reusable [`ruinivist/kde-6-widget-starter` workflow at the exact revision used](https://github.com/ruinivist/kde-6-widget-starter/blob/9d03fdbf66b190c39d997b2f60af24f658e77614/.github/workflows/reusable-pling-upload.yml) runs on GitHub-hosted `ubuntu-24.04`, takes a product ID and `PLING_USERNAME`/`PLING_PASSWORD`, and builds a widget ZIP. [NowPlaying's run](https://github.com/ruinivist/NowPlaying/actions/runs/45048475771) on 2026-11-22 for `release-v1.6.1` reported the actual [upload step successful](https://api.github.com/repos/ruinivist/NowPlaying/actions/runs/45048475771/jobs). [Independent OCS readback of product 2195583](https://api.kde-look.org/ocs/v1/content/data/2195583) shows changed `2026-11-22T17:17:21+00:00`, uploaded file version `1.6.1`, **product version `1.5`**. The date bump can still trigger a KNewStuff update; it does not make the advertised product version correct.
- The [script at the used revision](https://github.com/ruinivist/kde-6-widget-starter/blob/9d03fdbf66b190c39d997b2f60af24f658e77614/scripts/pling_upload.py) scrapes the OpenDesktop login form and dynamic hidden fields (including CSRF), submits email/password, retains session cookies, then discovers upload configuration and add/update/delete routes in the owner edit page. The multipart file upload uses edit-page-discovered file server URL, client/owner/collection identifiers; JSON from the file server is then registered against the product via its `addpploadfile` web route. The corresponding `updatepploadfile` sets **file** version; `getupdatesajax`/`saveupdateajax` use a distinct title/text changelog feed. These pieces show a real Pling file service behind the web app, not a documented standalone CI API or proof that its identifiers grant author permission. The production product's public [OCS output](https://api.kde-look.org/ocs/v1/content/data/2374098) shows a tokenized `/api/files/download/j/…` on `files06.pling.com`; that is a download URL, not upload auth.
- This script defaults to deleting **all** files first and reruns some failed write requests without transactional guarantees. `--dry-run` still signs in and discovers the owner edit endpoints. Changelog + file version are coupled to parsing `KPlugin.Version` via `zipfile.ZipFile`; the `.tar.gz` here is incompatible with that code path. It has no MFA/captcha handling, has a hard-coded verification-cookie shortcut, and assumes current HTML/JavaScript, AJAX request shapes and file server behavior. Do not use that shortcut or run the script as-is. Its most recent visible [script history](https://github.com/ruinivist/kde-6-widget-starter/commits/main/scripts/pling_upload.py) includes an upload/User-Agent breakage fix and changelog changes on 2026-09-12. No official or maintained general-purpose Marketplace publisher was identified; the reusable workflow is a community example.
- [Playwright's auth documentation](https://playwright.dev/docs/auth) describes persisted browser state and warns it can impersonate the account and expires. [GitHub's security guidance](https://docs.github.com/en/actions/reference/security/secure-use#hardening-for-self-hosted-runners) says self-hosted runners should almost never be used on public repos because untrusted workflow code can persist and compromise the runner. [GitHub environment protections](https://docs.github.com/en/actions/deployment/targeting-different-environments/managing-environments-for-deployment) can restrict deployment refs and require approval before environment secrets are released; they do not turn a shared persistent host into an isolated environment.

### Inferences

1. **Start with no store secrets.** After a successful final `release` job, use its tag/version and already-generated files to present the owner with the exact archive, `SHA256SUMS`, BBCode, and edit link. Add a read-only drift summary, with bounded checks for eventual consistency and separate “could not read” vs “version behind” results. A daily or manually triggered comparison of the latest final release against 2374098 also catches forgotten updates and permits readback after the manual save; deduplicate notifications per expected version. Put the release and drift check in the existing workflow or use an explicit schedule/dispatch rather than relying on a release created with the repo's `GITHUB_TOKEN` to trigger a new workflow ([GitHub trigger behavior](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#triggering-a-workflow-from-a-workflow); [current workflow](https://github.com/Alamion/heroes_III_ts/blob/testing/.github/workflows/release.yml)). Store drift should stay visible without blocking GitHub Releases or Pages. The currently observed manual catch-up target is **0.2.0**.
2. **Get support confirmation and validate the real upgrade before any unattended write.** Follow the public publishing API proposal or ask OpenDesktop for a supported sandbox/API and credential lifecycle. If authorized to test the normal UI, start with an ordinary interactive owner session, an approved test listing and a known package; independently check product Version, download version/filename, bytes, changelog feed and Plasma upgrade. Test same-tag reruns, interruption after adding the new file, rollback and removal of only the known superseded file. Keep a global per-product serial gate and skip stale releases/no-op reruns. Promote/verify the replacement before retiring the known old file; do not retry uncertain non-idempotent writes blindly.
3. **Fallback if the store permits it: approved, attended browser assist.** A small owner-run Playwright script could prefill the existing product's file/version/changelog in a normal browser and leave the final save to the owner. A GitHub-hosted writer would need a fresh login or to import a sensitive owner session on every ephemeral run; challenge, MFA where required, session invalidation, login-flow changes or 403 must stop the job and hand back to the owner. A self-hosted runner could retain a dedicated browser profile and support ordinary interactive re-authentication, but changes neither provider permissions nor the need for human intervention. Prefer the local owner-run helper over attaching a credential-bearing persistent runner to this public repo. If a runner is still justified, isolate it in a dedicated private deployment context with no untrusted code, restricted approved releases, minimal permissions, verified release artifacts and SHA-pinned dependencies; never use the owner's everyday machine/profile or expose the profile in CI logs, traces, caches or artifacts. Plan for upkeep of the browser, runner and selectors, plus periodic re-authentication and credential revocation. Human login/challenge completion in the normal UI only; no bypass or retries against denial.

### Gaps

- No authenticated test for product 2374098, no provider permission for UI automation verified, and no evidence of the owner's actual login/MFA requirements, session TTL, anti-bot behavior by runner origin, or a durable private product-update action. The November community success is specific to its workflow, account, and date. Publishing via browser, scraping product edit, and a runner retaining sessions remain maintenance-heavy fallbacks rather than verified full automation.
