## R0. Game executable selection (new)

**Decision**: a spike (S0) picks the capture executable in this order:

1. **Original `Heroes3.exe`** in the staging root (R1) on Xvfb, with `xdotool` input. The input
   failure seen on the desktop is typical of fullscreen DirectDraw pointer grabs under
   XWayland; Xvfb has no compositor or pointer confinement, so it may not occur. If input still
   fails, retry once under a Wine virtual desktop (`explorer /desktop=h3ref,800x600`) on the same
   Xvfb display, which is the usual Wine workaround for this game.
2. **HD Mod fallback**: `Heroes3_HD.exe` launched directly (as `HD_Launcher.exe` does) from a
   staging root that includes the HD Mod files (never HotA files), with a pinned vanilla profile
   written to the staging copy of `_HD3_Data/Settings/sod.ini`: `Graphics.Resolution = 800x600`,
   all scaling off, `HD+ = 0`, `Fix.Cosmetic = 0`, `UI.AdvMgr.HigherFPS = 0`,
   `UI.DarkTransitions = 0`, `UI.AdvMgr.SkipMapMsgs = 0`, `Graphics.SystemCursors = 1`, auto
   update off. Exact key semantics are checked in S0 against the launcher UI.

The selection is stored in local calibration (`gameExecutable: "original" | "hd-mod"`) and in
every record. If S0 selects `hd-mod`, implementation pauses for a constitution amendment
(Principle II currently forbids HD Mod as baseline) before stills are treated as baseline.

**Rationale**: keeps the unmodified executable whenever it can be driven; the fallback keeps the
original engine's adventure-map rendering with HD Mod's visible changes switched off, and is
honest about the difference in records.

Items marked **Spike** are design decisions whose concrete parameters (coordinates, value
names, timings) must be measured against the running game in the first implementation tasks.
The design does not change with the measured values; only calibration data does. Calibration
data derived from game output (pixel probes, signatures) is stored locally, never committed.

## R1. Running the baseline without touching the bundle

*(Paths below referring to `_HD3_Data/Heroes3.exe` now mean the Complete folder's top-level
`Heroes3.exe`; see Update 2026-09-14.)*

**Decision**: Build a git-ignored **staging game root** in a local state directory
(`$XDG_STATE_HOME/h3-reference/`, default `~/.local/state/h3-reference/`) containing: a *copy* of
`_HD3_Data/Heroes3.exe`, symlinks to the original runtime DLLs and to the original (non-HotA)
data archives, an empty `Games/`, and a `Maps/` folder that holds only the map(s) needed for the
current capture. Run it with a **dedicated Wine prefix** in the same state directory.

**Rationale**:

- Only whitelisted files are visible, so HotA (`HotA.dll`, `HotA*.lod`) and HD Mod
  (`_HD3_.dll`, `patcher_x86.dll`, `HD_*.dll`) cannot be loaded by accident; FR-004 holds by
  construction, and a `WINEDEBUG=+loaddll` log gives proof for the doctor.
- The bundle is never written; the user's `~/.wine` prefix and its registry are never touched.
- A one-map `Maps/` folder makes the scenario list deterministic (one entry, pre-selected).
- A dedicated prefix gives a clean, script-controlled registry for game settings (R4).

**Alternatives considered**:

- Copy `Heroes3.exe` into the bundle root and run there: modifies the bundle, HotA/HD DLLs sit
  next to the exe, HotA auto-update may interfere. Rejected.
- Copy the whole game (~1 GB) to the state dir: works but wasteful; symlinks suffice under Wine.
- Use the user's `~/.wine` prefix: settings would leak into their HotA play. Rejected.

## R2. Virtual display and driving input

**Decision**: `Xvfb` on an auto-selected display number (`-displayfd`), screen `800x600x24`
for the game and `1280x1024x24` for the editor. Wine runs with `DISPLAY` set to it,
`WAYLAND_DISPLAY` unset, and the prefix registry forcing the X11 graphics driver
(`HKCU\Software\Wine\Drivers\Graphics=x11`). Input via `xdotool` targeting that display
(mouse moves/clicks at fixed coordinates, key presses, `type` for the cheat text). Cleanup:
`wineserver -k` for the dedicated prefix, then terminate Xvfb.

**Rationale**: fully invisible to the KDE Wayland session (FR-012, SC-008); XTEST input only
reaches the virtual display; the game's native 800×600 equals the screen, so "full screen" mode
is a no-op and pixels are exact. Killing the dedicated prefix's wineserver cannot affect other
Wine programs.

**Alternatives considered**: `gamescope` nested/headless (heavier, Vulkan path, scaling risk);
KWin nested Wayland session (Wine's X11 path still needed; more moving parts); Xephyr (visible
window). Xvfb is the smallest dependency that satisfies "never shown".

## R3. Screenshots and clips

**Decision**:

- **Still**: `ffmpeg -f x11grab -draw_mouse 0 -video_size 800x600 -i :N -frames:v 1` → PNG
  (lossless, native pixels). For analysis (stability wait, minimap readback, volatile mask) the
  same grab is read as `rawvideo rgb24` into Node buffers.
- **Volatile mask**: each still capture also grabs K frames (default 12 over ~2 s) and marks
  every pixel that changed in any of them; stored as a 1-bit PNG mask next to the still.
  Reproducibility (SC-002) compares only pixels unmasked in both captures.
- **Clip**: `ffmpeg -f x11grab -framerate 60 -draw_mouse 0` cropped to the adventure-map
  viewport, piped as raw frames to Node with wall-clock timestamps; consecutive byte-identical
  frames are merged into one **distinct frame** with `[tStartMs, tEndMs)`; distinct frames are
  written as PNG plus a `frames.json` timeline. The record stores grab rate, measured shortest
  distinct-frame duration, and a `resolvesAllSteps` flag = (grab interval ≤ ½ shortest step).
- **Cursor**: `-draw_mouse 0` drops the X cursor. Spike S4 checks whether the game also draws a
  software cursor; if it does, the mouse is parked at a calibrated screen point outside the
  viewport with no hover effect before every grab, and the record notes the park point.

**Rationale**: `ffmpeg` is already installed; exact dedup keeps clips small while preserving
every animation step and its timing (FR-007, SC-004); no npm image library needed (VIII).

**Alternatives considered**: `xwd`/ImageMagick `import` (extra packages, no clip path);
lossless video only (consumers would need a decoder; frame-at-time lookup harder); fixed-rate
PNG dump without dedup (hundreds of MB per clip).

## R4. Fixed game settings

**Decision**: settings live in the dedicated prefix registry under the SoD key
(`HKCU\Software\New World Computing\Heroes of Might and Magic® III\1.0`). The tooling writes a
typed **settings profile** (data module) as a `.reg` import before each launch and reads it back
to verify (FR-005). Profile intent: intro videos off (if a value exists), music and sounds off,
hero/computer walk speed and map scroll speed fixed at documented values, animation options at
game defaults.

**Spike S1**: first launch with a clean prefix, change each adventure option in the game UI,
diff the registry, and record exact value names and encodings in the settings data module.

**Rationale**: registry import is scriptable and verifiable; a clean dedicated prefix gives a
known starting state.

**Alternatives**: clicking through the options dialog on every run (slow, fragile).

## R5. Reaching the adventure map

**Decision**: a typed **navigation script** (data module) of steps — each step is an action
(click at point, key, type text, wait) followed by a *wait-until* condition: screen stable for
N consecutive identical grabs, optionally plus a match against a locally calibrated probe
region. Default flow for Heroes3.exe: skip intro/logos (Esc/click) → main menu *New Game* →
*Single Scenario* → (one map listed) *Begin* → dismiss start dialogs → adventure map.

**Spike S2**: measure click coordinates at 800×600 and record local probe signatures with a
`calibrate` command. Signatures are hashes of small screen regions of game output, stored in
the state directory (git-ignored), never in the repo (Principle I).

**Rationale**: fixed resolution makes coordinates constant; stability waits make timing
independent of machine speed; per-step timeouts turn hangs into typed failures (FR-013).

**Alternatives**: command-line map launch (SoD has none known); HD Mod quick-start (not
allowed — HD Mod must not be loaded).

## R6. Removing fog of war

**Decision**: after the adventure map is ready, open the in-game message line and type
`nwctheone`, then Enter. Verify by reading the minimap: after reveal, no minimap pixel of the
current level may have the shroud color. If verification fails, the capture fails with
`REVEAL_FAILED` (spec edge case).

**Confirmed 2026-09-14** (developer, HD Mod build): `nwctheone` and `nwcwhatisthematrix` reveal
the map. **Spike S3** only confirms the key that opens the message line (expected `Tab`) in the
selected executable. The cheat text is a configuration value in the
settings data module; if it does not reveal the map, candidates to test are the SoD codes
`nwcwhatisthematrix` / `nwcrevealourselves`, and the spec clarification is updated with the
result.

**Rationale**: user-provided method; minimap verification is cheap and independent of the
viewport.

## R7. Positioning the view and reading back the actual view (discovery)

The game has no "go to coordinates" command and shows no coordinates in the unmodified build,
so both **moving** the view and **proving** where it is are discovered in Spike S5.

**Confirmed 2026-09-14**: candidate 1 (minimap click centers the view) works, and the view
rectangle is a dashed red outline on the minimap. S5 now only measures minimap geometry,
rectangle color/dash pattern, edge clamping, and verifies the 10/10 rule below; candidates 2–3
remain documented fallbacks.

**Decision (moving) — candidates tested in this order, first that passes wins**:

1. **Minimap click**: the minimap maps the whole level onto a fixed square (144×144 px in the
   800×600 layout, to be measured). Clicking the pixel for tile (x, y) centers the view on it.
   Tile → minimap pixel = `floor((x + 0.5) * side / mapSize)`. Exact for maps ≤ 144 tiles wide.
2. **Minimap click + arrow-key correction**: click near the target, read back the view (below),
   then press arrow keys one tile at a time until the view origin equals the target.
3. **Anchor + arrow keys**: centre on a known start (hero/town at game start), then arrow keys.

**Decision (reading back) — used by every capture (FR-011)**:

- **Minimap view rectangle**: the game draws the visible area as a rectangle on the minimap.
  Detect it in the minimap region (rectangle color calibrated in S5) and convert its edges to
  tile coordinates. For maps ≤ 144 tiles this is exact to the tile; the record stores the
  resulting visible tile range and tile-to-pixel mapping, and `positionSource: "minimap-rect"`.
- **Cross-check for SC-003**: register the game viewport against an editor capture of the same
  area (32 px grid offsets only, masking volatile pixels). This is a verification step in the
  self-check, not a per-capture requirement.

**Spike S5 success rule**: for 10 random tiles on both levels of `Arrogance.h3m`, the move
method yields the requested origin (or the clamped edge origin), the minimap readback agrees
with the editor registration 10/10, and repeating the request gives identical viewport pixels
outside the volatile mask.

**Also measured in S5**: viewport rectangle on screen (the 32 px grid origin and visible
columns/rows, including partial edge tiles), level switch control (button and/or key),
edge-clamping behaviour.

**Alternatives considered**: prepared scenario with a hero moved to the target (needs map
editing; more derived files); pixel-registering against the project's own renderer (circular —
the renderer is what captures are meant to verify).

## R8. Map editor captures

**Update 2026-09-14**: the original `h3maped.exe` is available and is used instead; it runs from
the same staging root as the game (plus its own DLL needs, found in S6), so no HotA files are
involved.

**Decision**: run the map editor from a staging root in the same dedicated prefix on a 1280×1024 virtual
display. Open the map via command-line argument if the editor honours it, else via the
File → Open dialog with a typed `Z:\…` path. Turn overlays (grid, passability, etc.) off through
the editor's menus/registry values; record overlay state. Position with the editor's
minimap/scrollbars and read back the view from the editor's own view indicator.

**Spike S6**: open method, overlay settings, viewport geometry, positioning control, and
whether the editor writes into its root (the doctor compares a hash/mtime manifest of the
bundle before and after to prove the bundle is unchanged).

**Rationale**: original editor; no constitution exception needed.

## R9. Capture storage and lookup

**Decision**: one directory per capture:
`reference-captures/<map-key>/<level>/<source>-<kind>/<UTC-timestamp>_x<x0>-<x1>_y<y0>-<y1>/`
with `record.json` plus `still.png` + `volatile-mask.png`, or `frames/NNNN.png` +
`frames.json`. `<map-key>` = NFC map file name without extension + `-` + first 8 hex of its
sha256 (unambiguous for non-ASCII and same-named maps). Lookup scans `record.json` files; no
separate index file until volume requires it (YAGNI; expected < 1000 captures). Directories are
created atomically (write to `.tmp-…`, then rename), so a failed capture never leaves a
half-record.

**Rationale**: human-browsable, never overwrites (timestamp + atomic rename), trivial to prune.

## R10. Tooling language, dependencies, concurrency

**Decision**: TypeScript under `tools/reference-env/`, run directly by Node 22 (type
stripping; imports with `.ts` extensions, erasable syntax only), invoked via `yarn ref <cmd>`.
No new npm dependencies. System packages (dev machine only): `wine`, `xorg-x11-server-Xvfb`,
`xdotool`, `ffmpeg`. Single-capture lock: exclusive-create lock file with PID in the state
directory; stale lock (dead PID) is taken over with a warning; a second command waits up to a
configurable time, then fails with `LOCKED`. Logging via a small level-gated stderr logger;
stdout carries only the JSON summary (FR-020).

**Rationale**: zero runtime/bundle impact; pure logic (records, lookup, geometry, frame dedup,
rectangle detection) unit-tested with synthetic buffers in Vitest.

**Alternatives**: `tsx`/`ts-node` dev dependency (unnecessary on Node 22); Python scripts
(second toolchain); shell scripts (poor typing/testing).

### 2026-09-14 — implementation spikes (S1–S6) and measurements

- **S1 settings:** a clean dedicated prefix has no game registry values and the original
  executable only writes them on a normal exit, which captures never do. Every capture therefore
  runs with the game's defaults; the settings profile (`defaults-clean-prefix-v1`) has no
  overrides and records that. Wine audio drivers are disabled in the prefix so captures are
  silent.
- **S2 navigation:** clicking (400, 300) repeatedly from 8 s after launch skips the logos and the
  intro; the main menu is the first screen that stays byte-identical. Fixed start (FR-009a):
  *Дополнительные настройки* (515, 518); per player row (y = 150/200/250/300) click town "next"
  (229) once, hero "next" (305) once, bonus "next" (382) twice → Castle, first Castle hero (human
  only; the game does not allow choosing AI heroes), gold. The advanced-options screen is
  byte-identical across launches. Remaining randomness in fixed mode: AI heroes and starting
  army sizes (right-hand panel, outside the viewport) and animation phases (volatile mask).
  The scenario intro message is detected by a locally recorded probe of its OK button.
- **S3 reveal:** `nwcwhatisthematrix` with Ctrl held; verified by the minimap shroud fraction.
  The reply "Обманщик!!!" covers the lower viewport for ~22 s (measured); the capture positions
  the view meanwhile and waits for the remainder of 25 s before grabbing.
- **S4 cursor:** the game draws its own cursor. The park point must not touch a screen edge —
  (700, 590) on the bottom edge scrolled the map. (690, 470) over the hero panel is used.
- **S5 view geometry:** minimap inner area (630, 26, 144×144); view rectangle colour
  (255, 73, 123); view = 19×17 tiles; a minimap click at tile T puts the view origin at
  T − (9, 8), also past the map edges (the game shows space beyond the map). The origin tile is
  drawn at screen (0, 8); viewport (8, 8, 592×544), so the outer columns are cut by 8 px. Verified
  on Arrogance for (0,0), (18,18), (35,35), (3,32), both levels. Level toggle button (727, 212);
  the level shown is recognised by a locally recorded probe of that button.
- **S6 editor:** `h3maped.exe <Z:\…\map.h3m>` opens the map directly; on a 1280×1024 display
  without a window manager the window is at (4, 30), 952×734. Map area (19, 124, 698×603), tile
  (origin) drawn at (19, 124), view 21×18 whole tiles; minimap (739, 111, 144×144); a minimap click
  at T gives origin clamp(T − (10, 9)). The view rectangle is drawn by inverting terrain colours,
  so it is detected as pixels whose inverse equals an adjacent pixel. Underground toggle (336, 64),
  grid toggle (360, 64). The editor keeps the host locale (English locale garbles its menus).
  **The editor animates objects too, but chooses their frames once per launch** (20 s static,
  repaints identical); the volatile mask therefore compares several launches (`--launches`,
  default 3). Two captures with 3 launches each differed in 50 of ~407 000 unmasked map pixels.
- **Clip timing:** water/animation steps are ~167–183 ms (≈5.5 fps); a 60 fps grab of 5 s gave
  300 frames → 29 distinct frames, `resolvesAllSteps: true`.
- **Game vs editor colours:** the game renders in 16-bit colour, so channels differ by a few
  levels from the editor; registration uses a per-channel tolerance of 8. For (10, 12) the true
  offset differs in 6 % of pixels (heroes, flags, editor markers) versus ≥ 99 % for any other.
- **Timings (this machine):** doctor 6 s; still ≈ 1 min 30 s; clip (5 s) ≈ 1 min 45 s; editor
  (3 launches) ≈ 42 s; calibrate ≈ 2 min.
- **Random map objects (selfcheck, 2026-09-14):** `selfcheck --runs 3 --samples 2` on Arrogance:
  position agreement 4/4 (both levels, offset (0, 0), 1.6–17.6 % tolerant differences from
  heroes/flags/editor markers); reproducibility **not** met — runs differed from run 1 in 39 and
  63 unmasked pixels, all on one tile whose *random monster* resolved to a different creature on
  each launch (Champion, Dragon Fly, Wolf). Random objects are rolled at game start, so fixed
  start choices cannot pin them. Options: (a) treat tiles with random objects as volatile once the
  foundation's H3M object parser can list them; (b) spike a deterministic game RNG (e.g.
  `libfaketime` for the game process; not installed). `selfcheck` now reports differing pixels
  per map tile so such tiles are visible.

### 2026-09-14 — after the Fedora 43 upgrade; libfaketime experiment

- **Re-verification on Fedora 43:** Xvfb 21.1.24, xdotool 3.20211022.1-9, ffmpeg is now the
  `ffmpeg-free` 7.1.5 package (x11grab present), Wine 11.0 Staging, Node 22.22.2. Type-check,
  unit tests, doctor, still (both levels), clip and editor captures all work unchanged.
- **Navigation hardening:** menu screens are now recognised by locally calibrated probes (button
  regions of the main menu, the new-game submenu and the scenario screen) instead of "screen
  stopped changing", which misfired when an intro frame paused and once walked into the campaign
  screen. Clicks wait for the screen to change before waiting for it to settle. Any failure saves
  a screenshot to `<stateDir>/failures/`. Old calibrations lack the new probes; doctor and
  captures ask for `yarn ref calibrate`.
- **libfaketime (0.9.12) to pin random map objects — not effective:**
  - Wine runs under `LD_PRELOAD=libfaketime.so.1` (a Windows program sees the fake date).
  - `FAKETIME="@2026-01-01 00:00:00"` (fixed start, clock running): 3 stills of Arrogance at
    (18, 18) — run 3 matched run 1, run 2 differed on the random-monster tile (20, 25).
  - Same, plus clicking *Begin* at a fixed 45.5 s after launch: 4 runs, all 3 comparisons
    differed on that tile.
  - Frozen real-time clock (`FAKETIME="2026-01-01 00:00:00"`, monotonic real): Wine itself
    crashes (WineDbg dialog). A fully frozen clock is therefore not usable either.
  - `Heroes3.exe` imports only `timeGetTime`, `GetLocalTime`, `GetSystemTime` as time sources.
    The observations fit a seed taken from the millisecond timer, or a clock-seeded generator that
    menu animations advance per frame — neither can be aligned by shifting the clock.
  - The experiment code was removed. Remaining options for FR-009/SC-002 on tiles with random
    objects: treat those tiles as volatile using the map's object list (needs the foundation's
    H3M object parser), or a separate spike that makes the game's time source deterministic at the
    API level (e.g. a Wine DLL override for `winmm.timeGetTime`), which is a larger change.

### 2026-09-14 — decision: floating tiles for random objects

- Tiles covered by random map objects are **floating**: automated reproducibility checks exclude
  them; their appearance is verified less often and visually. `yarn ref selfcheck
  --floating-tiles "x,y;x,y"` reports differences on such tiles separately (`floatingTiles`) and
  does not fail on them. The list will come from the H3M object parser (TODO item 2); until then
  it is given by hand (Arrogance: `20,24;21,24;20,25;21,25` for the view centred on (18, 18)).
  A floating area is the object's whole sprite footprint, not only its tile: monster sprites are
  2×2 tiles (up and left of the object tile), so a large creature also changes the tile above —
  the first full run showed differences on (21, 24).
- Verified: `selfcheck --runs 3 --samples 0 --floating-tiles "20,24;20,25;21,25"` → ok, 0 differing
  non-floating pixels in both comparisons (3 min 50 s).
- If specific random outcomes need verifying, an object atlas (as in the PoC) on a separate git
  branch is inspected directly instead of relying on a map.

### 2026-09-14 — full live test run: fixes

The first full `H3REF_LIVE=1` run found three problems, all fixed:

- **`По праву силы.h3m` is a HotA map** (format 0x20), not a base-game map; the tooling rejects it
  correctly with `MAP_UNSUPPORTED`. The non-ASCII name check now uses a temporary renamed copy
  of Arrogance, and the live suite asserts the HotA rejection separately.
- **Non-ASCII map file names:** under the English locale the game lists no scenario for a
  Cyrillic file name and falls back to the random-map screen. Maps are now staged as
  `Maps/reference.h3m` (records keep the original name), and navigation fails with
  `MAP_UNSUPPORTED` when the scenario name field is empty (yellow text pixels: 401 listed vs 0 on
  the random-map screen). The scenario screen's left-hand art is random per launch, so it is not
  used as a probe.
- **Clipped view rectangle misread:** a click on tile y = 7 of Arrogance *does* give view origin
  y = −1, but the rectangle's top edge is clipped and the side dashes can start in a dash gap below
  the minimap top, so the bounding box looked unclipped and was read as origin 0 (the game-vs-editor
  registration exposed a one-tile shift). Edges are now recognised as drawn only when a dashed line
  runs along them. Correction clicks also move by whole tiles in minimap pixels (the old 1 px step
  was below one tile on 36×36 maps).
- **Occasional crash under Wine:** once `Heroes3.exe` hit an unhandled page fault while loading a
  map (not reproducible on retry). `winedbg` is disabled in the prefix so a crashed game exits;
  a capture whose game process exited fails with `GAME_CRASHED` and is retried once.
