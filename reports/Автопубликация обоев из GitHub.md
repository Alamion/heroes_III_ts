# Prepare store updates from GitHub

**GitHub Actions can prepare and verify both store updates today; neither production item has a verified unattended publishing path.** For [KDE Store product 2374098](https://store.kde.org/p/2374098/), another project demonstrably uploaded to Pling from a GitHub-hosted runner, but its script left the product version stale and relies on undocumented web forms. For [Wallpaper Engine Workshop item 3808342201](https://steamcommunity.com/sharedfiles/filedetails/?id=3808342201), the Windows editor is the confirmed publishing route; SteamCMD and direct Steamworks uploads remain unverified for Wallpaper Engine’s app **431960**. As of the November 27, 2026 checks, GitHub’s latest final release was **0.2.0**, KDE reported **0.1.4**, and Steam’s latest visible change note was **0.1.4**; the Steam note does not establish what bytes subscribers receive ([GitHub release](https://api.github.com/repos/Alamion/heroes_III_ts/releases/latest), [KDE readback](https://api.kde-look.org/ocs/v1/content/data/2374098), [Steam change notes](https://steamcommunity.com/sharedfiles/filedetails/changelog/3808342201)). Start with a credential-free KDE handoff and drift check; keep the existing owner-confirmed store updates.

## KDE: a real upload succeeded, but the product version stayed stale

**Confirmed:** KDE’s public OCS endpoint reports product version, change date and downloadable file metadata. The OCS standard specifies authoring operations, but providers can implement a subset; no supported write endpoint or product-scoped credential was verified for this provider. The public product page returned an Anubis challenge to the research client. An October update to the KDE publishing proposal reported secondhand that OpenDesktop planned a documented API, without publishing a usable contract ([OCS specification](https://www.freedesktop.org/wiki/Specifications/open-collaboration-services/#content), [KDE Discuss proposal](https://discuss.kde.org/t/proposal-official-ci-cd-publishing-workflow-for-kde-store-opendesktop/50377)).

**Working example:** NowPlaying’s November 22 `release-v1.6.1` run [45048475771](https://github.com/ruinivist/NowPlaying/actions/runs/45048475771) reported a [successful upload job](https://api.github.com/repos/ruinivist/NowPlaying/actions/runs/45048475771/jobs) using the [pinned Pling workflow](https://github.com/ruinivist/kde-6-widget-starter/blob/9d03fdbf66b190c39d997b2f60af24f658e77614/.github/workflows/reusable-pling-upload.yml). [OCS readback for product 2195583](https://api.kde-look.org/ocs/v1/content/data/2195583) independently showed file version **1.6.1** and a fresh change date, while product Version remained **1.5**. Its [uploader at the same revision](https://github.com/ruinivist/kde-6-widget-starter/blob/9d03fdbf66b190c39d997b2f60af24f658e77614/scripts/pling_upload.py) uses account credentials and undocumented browser endpoints, defaults to deleting all files before replacement, and expects a ZIP for version extraction where this project ships a `.tar.gz`. Even its dry run signs in. Do not adopt it as-is or bypass anti-bot checks. If OpenDesktop permits an attended browser helper, keep it local and leave sign-in, challenges and final save to the owner.

**Workaround to test after approval:** OpenDesktop [announced GitHub file links](https://blog.opendesktop.org/github-file-links/) in 2017. Check whether today’s **Files** editor accepts a downloadable link on a permitted test listing. Start with the [existing tagged archive](https://github.com/Alamion/heroes_III_ts/releases/download/v0.2.0/heroes3-living-map-kde-0.2.0.tar.gz); verify OCS download metadata, the fetched checksum, and a clean Plasma 6 installation. Only then test a moving link. The [proposed stable alias](https://github.com/Alamion/heroes_III_ts/releases/latest/download/heroes3-living-map-kde.tar.gz) returned 404 because the unversioned asset is absent. If added, ensure the alias serves checked bytes before pointing the store at it. A moving URL can refresh **new downloads**, but KNewStuff compares cached product version or update date, not the archive’s internal version or the redirect target. Keep the Version and changelog edit, and verify an actual upgrade after a Version bump before changing production ([GitHub stable asset links](https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases), [KNewStuff update logic](https://github.com/KDE/knewstuff/blob/master/src/attica/atticarequester.cpp)).

## Steam: stage locally and publish through the editor

**Confirmed:** The Wallpaper Engine editor documents updates to an existing item; its [CLI](https://help.wallpaperengine.io/en/functionality/cli.html#command-overview) can open or preview wallpaper but has no publish command. Use a clean, dedicated Windows editor project with the checked package and `workshopid` **3808342201**. Keep the change note outside that directory and all game files out: the editor uploads the whole folder. The owner confirms **Publish update**, preserves **Everyone** and existing visibility, and checks the note and a subscriber installation ([editor guide](https://docs.wallpaperengine.io/en/scene/first/publishing.html#publishing-updates), [project procedure](../docs/releasing.md#4-update-the-steam-workshop-item)).

**Unverified for 431960:** Valve documents SteamCMD’s `workshop_build_item` as a testing route; [Bannerlord’s pipeline](https://github.com/BUTR/workflows/blob/master/.github/workflows/release-steam.yml) shows another app using it. Steam Guard codes or cached sessions authenticate an account without establishing write permission for this app. A direct `ISteamUGC` client needs a running Steam client in the same OS user/privilege context, a licensed account with rights to the item, and the right app context and publisher-side configuration. `steam_appid.txt` supplies context only; publishing from a different app ID requires Steamworks App Publish Permissions. Neither SteamKit protocol definitions nor Valve’s PublishedFile Web API establish an owner-accessible file uploader. Ask Wallpaper Engine first; if supported and separately authorized, test content and a change note only on a **private editor-created Web item**. Confirm the callback and actual subscriber install before considering production; check the outcome before retrying an ambiguous submission ([Valve Workshop guide](https://partner.steamgames.com/doc/features/workshop/implementation), [Steam API initialization](https://partner.steamgames.com/doc/api/steam_api#SteamAPI_Init), [UGC reference](https://partner.steamgames.com/doc/api/ISteamUGC)).

## Prove the handoff before granting publish access

The [release workflow](../.github/workflows/release.yml) already builds `release-assets` before all checks finish; the `release` job waits for those checks. Use a manual dispatch on `testing` with **v0.2.0**, [run 40677211348](https://api.github.com/repos/Alamion/heroes_III_ts/actions/runs/40677211348), and KDE as the first store. Verify the exact repo, workflow, successful tag-push run and release job, tag commit, final release status and artifact ID. Check the fixed nine-file manifest and compare the archive and changelog hashes to the [published checksums](https://github.com/Alamion/heroes_III_ts/releases/download/v0.2.0/SHA256SUMS). The public release files were hash-verified; downloading the Actions ZIP with a job token remains part of the proof. Show the verified files, target and OCS drift without store credentials or writes. Repeat for identical hashes; reject wrong or failed runs, stale or prerelease input, tampering and expired artifacts.

Later, `workflow_run: completed` can trigger preparation with the same checks; `release: published` can fire before attachments from a human-created release and normally will not start downstream CI when caused by `GITHUB_TOKEN` ([GitHub workflow triggers](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#triggering-a-workflow-from-a-workflow)). Any approved writer should serialize per item across versions, reject downgrades, skip proven repeats and reconcile partial writes before retrying. Keep personal store sessions off this public repo’s runners.
