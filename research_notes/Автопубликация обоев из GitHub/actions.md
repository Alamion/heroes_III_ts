# Store updates from existing GitHub Actions release artifacts

## 1. Which release outputs and checks can be reused?

### Takeaway
The existing `release-assets` artifact contains the store payloads already. Consume the original checked bytes, with a gate on successful release publication; the artifact can exist before all checks pass.

### Cited Findings
- `.github/workflows/release.yml` is triggered by a `v*` tag push or dispatch with an explicit existing tag. `check` emits `version` and `prerelease`; `hosts` runs a four-host simulation matrix; `build` runs the production build, tests, packaging, reproducibility checks and `yarn verify store-texts`, then uploads `dist/release/<version>/` as `release-assets`. The `release` job waits for all three, downloads that same artifact and publishes via `yarn release publish`. `pages` follows `release` for finals only. `.github/workflows/ci.yml` is a separate push/PR check workflow and is not a release source. — [release workflow](../../.github/workflows/release.yml#L8-L143), [ordinary CI](../../.github/workflows/ci.yml#L5-L39)
- `tools/release/tags.ts` owns tag/package version equality, tagged commit ancestry on `origin/testing`, changelog validation, and the final-version comparison against all other valid final `v*` tags (not the Releases UI). `tools/release/semver.ts` owns ordering and prerelease detection, rejects build metadata, and applies the Lively integer bounds. The version originates in `package.json`; the changelog is hand-maintained. — [tag rules](../../tools/release/tags.ts#L47-L123), [SemVer](../../tools/release/semver.ts#L12-L70), [release instructions](../../docs/releasing.md#L14-L38)
- `tools/package/cli.ts` owns archive naming (`artifactName`); `tools/release/build-assets.ts` and `assets.ts` assemble the release directory. `SHA256SUMS` covers **nine** files (four host archives and five store texts), in `sha256sum -c` format. `release-notes.md` is in the Actions directory, is not included in `SHA256SUMS`, and is used for the GitHub Release body only. The versioned payloads needed here are `heroes3-living-map-wallpaper-engine-<version>.zip` plus `changenote-<version>.bbcode`, and `heroes3-living-map-kde-<version>.tar.gz` plus `kde-changelog-<version>.bbcode`; the optional listing texts are `workshop-title.txt`, `workshop-description.bbcode`, `kde-store-description.bbcode`. Web and Lively do not have a new store destination. — [packager](../../tools/package/cli.ts#L60-L75), [release asset builder](../../tools/release/build-assets.ts#L25-L44), [checksum writer](../../tools/release/assets.ts#L37-L60), [text filenames](../../tools/release/store-texts.ts#L88-L95), [manual procedures](../../docs/releasing.md#L78-L113)
- `tools/release/store-texts.ts` and `markup.ts` own formatting from `CHANGELOG.md`, `docs/store/` and shared bilingual strings. Text checks cover UTF-8 byte limits, allowed BBCode, project-only links in descriptions (not changelogs), affiliation wording, and version-tagged documentation image links. `src/adapters/shared/project.ts` owns the fixed Workshop ID `3808342201` and KDE product URL `/p/2374098/`. Package checks verify Workshop ID/KDE package version and reject game content. The constitution forbids redistributing game files and derived content in CI/store packages; the documentation screenshot exception allows manual gallery upload by the maintainer and excludes screenshots from packages, release assets and build output. — [text and markup owners](../../tools/release/store-texts.ts#L77-L129), [markup](../../tools/release/markup.ts), [project identities](../../src/adapters/shared/project.ts#L16-L36), [package checks](../../tools/checks/packages/index.ts#L76-L85), [manifest checks](../../tools/checks/packages/index.ts#L186-L201), [constitution I](../../.specify/memory/constitution.md#L70-L91)
- Verified live without credentials: the repo is public (personal owner, default branch `testing`). Release run `40677211348` is a successful `push` for `v0.2.0` with workflow ID `367837852`; all eight jobs succeeded, and the run lists unexpired artifact `release-assets` ID `12811217099` with a digest and matching tag commit `60584121697a3304d844d61a789633b8230580ac`. The public Actions ZIP endpoint returned `401` without authentication. The corresponding GitHub Release is final, not draft, and mutable (`immutable: false`); I streamed all nine public payload files and independently verified their SHA-256 against its `SHA256SUMS`, also matching the nine published digest fields. This validates the release asset interface; it does not independently validate byte equality against the Actions ZIP. — [repository metadata](https://api.github.com/repos/Alamion/heroes_III_ts), [run](https://api.github.com/repos/Alamion/heroes_III_ts/actions/runs/40677211348), [job results](https://api.github.com/repos/Alamion/heroes_III_ts/actions/runs/40677211348/attempts/1/jobs), [artifact metadata](https://api.github.com/repos/Alamion/heroes_III_ts/actions/runs/40677211348/artifacts), [tag ref](https://api.github.com/repos/Alamion/heroes_III_ts/git/ref/tags/v0.2.0), [release metadata](https://api.github.com/repos/Alamion/heroes_III_ts/releases/tags/v0.2.0), [public checksum file](https://github.com/Alamion/heroes_III_ts/releases/download/v0.2.0/SHA256SUMS)

### Inferences
- Keep packaging and text generation in their current owners and keep the store consumer under release tooling. The missing pieces are provenance validation, strict downloaded-file verification and the store handoff; neither `yarn release texts` (which may omit change notes) nor `yarn release publish` (which enumerates files and writes to GitHub) is a store preparation command. — [text-only behavior](../../tools/release/build-assets.ts#L47-L61), [publisher behavior](../../tools/release/publish.ts#L22-L53)
- In a secret-free GitHub-hosted job, pin the artifact to the source run and immutable artifact ID. Validate the exact nine-entry checksum manifest (reject missing, duplicate or unexpected paths before hashing), verify file bytes, expect only that fixed set plus the checksum file and the unused notes, then select the fixed host archive/text names. Use a fresh temp directory outside the checkout. Treat archives and BBCode as data; never use downloaded files as job code. If the store needs a directory, inspect archive paths/entry types and package identity, extract into fresh staging and give it only the selected payload, never a working project directory. A checksum supplied alongside its files detects corruption but does not establish trust in their producer. — [existing checksum format](../../tools/release/assets.ts#L37-L60), [GitHub artifact security example](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#using-data-from-the-triggering-workflow), [manual warning about uploading the entire folder](../../docs/releasing.md#L84-L99)

### Gaps
- Actual repository Actions ZIP download and content verification with the same-repository job token require an authorized run; public metadata and GitHub Release files were the available evidence. — [artifact endpoint](https://api.github.com/repos/Alamion/heroes_III_ts/actions/artifacts/12811217099/zip), [GitHub's cross-run token example](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#using-data-from-the-triggering-workflow)

## 2. Which trigger and trust boundary should launch the update?

### Takeaway
Start with a separate `workflow_dispatch` workflow on `testing`, using an exact successful release run as an input. An automatic `workflow_run` completion trigger is viable later if it runs the same provenance checks. A GitHub `release: published` trigger is unsuitable for the current producer.

### Cited Findings
- `workflow_dispatch` requires the workflow on the default branch, but the run's `GITHUB_REF` is the branch or tag selected at dispatch. `workflow_run` also requires the workflow on the default branch and uses that default branch as its own ref/SHA. `completed` fires regardless of upstream result; filter on `conclusion` explicitly. An upstream `workflow_dispatch` run's `head_sha` refers to its dispatch ref, whereas this repository builds the separate `inputs.tag` checkout. The observed tag-push run's `head_branch` is the tag name. — [manual-dispatch event](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch), [workflow-run event](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run), [tag checkout](../../.github/workflows/release.yml#L28-L49), [observed source run](https://api.github.com/repos/Alamion/heroes_III_ts/actions/runs/40677211348)
- The publisher uses `GITHUB_TOKEN`; events caused by that token generally do not create workflow runs (`workflow_dispatch` and `repository_dispatch` are exceptions, with a separate PR exception). Also, a maintainer can create the GitHub Release before the build and asset upload; the publisher itself creates/edits the Release and only then uploads files. Thus a human-caused `release: published` can occur too early, while a token-caused one will not start the downstream workflow. — [GitHub token trigger rules](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#triggering-a-workflow-from-a-workflow), [release job token](../../.github/workflows/release.yml#L124-L129), [publish order](../../tools/release/publish.ts#L29-L53), [manual tag/release paths](../../docs/releasing.md#L40-L57)
- The platform supports listing artifacts by exact run, and download by ID. Artifact v4 uploads are immutable per ID, deletable/recreatable under a new ID, and subject to retention. GitHub's cross-run example uses the workflow token with `actions: read`; download defaults to the current run unless `github-token` and `run-id` are supplied. — [Actions REST artifact API](https://docs.github.com/en/rest/actions/artifacts#list-workflow-run-artifacts), [download-artifact v4 inputs](https://github.com/actions/download-artifact/tree/v4#inputs), [upload-artifact v4 retention and replacement](https://github.com/actions/upload-artifact/tree/v4#retention-period), [GitHub workflow_run example](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#using-data-from-the-triggering-workflow)
- `workflow_run` may receive secrets and a write token regardless of upstream privileges; GitHub calls out untrusted code checkout, cache poisoning and treating artifacts cautiously. GitHub-hosted runners are isolated per run; public-repo self-hosted runners can be persistently compromised and environment approval does not isolate them. GitHub recommends dependency locking or full action commit SHAs, minimum token permissions, and avoiding direct interpolation of untrusted values into shell scripts. — [secure use](https://docs.github.com/en/actions/reference/security/secure-use), [self-hosted hardening](https://docs.github.com/en/actions/reference/security/secure-use#hardening-for-self-hosted-runners)
- Required reviewer approval precedes environment secret access. Selected deployment branches/tags match **the downstream run's** `GITHUB_REF`, not a tag passed as an input or found in an upstream event. The public repo currently lists only `github-pages` with a branch policy; the existing Pages environment is unsuitable for store-specific credentials. — [environment rules](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments#deployment-branches-and-tags), [environment secrets](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments#environment-secrets), [public environment list](https://api.github.com/repos/Alamion/heroes_III_ts/environments)

### Inferences
- Recommended first source contract: manual dispatch on `refs/heads/testing`, exact numeric release run ID, exact canonical final tag, and one fixed store choice. Verify repository and head repository, workflow ID/path, supported source event, completed/successful status, and a successful `release` job; require tag, peeled SHA, source run, artifact and non-draft/non-prerelease GitHub Release with expected uploaded assets to agree. Initially accept only a source tag-push run (both event and tag/SHA checks); do not infer the target from `head_branch`, `head_sha`, `display_title`, or a filename for an upstream dispatch. To admit upstream dispatch or more complex partial reruns, have the producer bind the **checked** tag/version/commit and source run plus build attempt and artifact ID/digest in an explicit handoff; its current `check` JSON contains commit/tag but the workflow forwards only version/prerelease and does not persist that JSON in the artifact. Guard mutable tag checkouts by passing the validated commit between jobs or protecting valid release tags from update/deletion. — [existing checkout/output contract](../../.github/workflows/release.yml#L24-L49), [later tag checkouts](../../.github/workflows/release.yml#L61-L85), [release check result](../../tools/release/tags.ts#L104-L123), [run jobs example](https://api.github.com/repos/Alamion/heroes_III_ts/actions/runs/40677211348/attempts/1/jobs), [environment ref rules](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments#deployment-branches-and-tags)
- Automatic variant: `workflow_run` for `release`, `completed`, validate exact upstream identity and release job as above, never select the most recent artifact globally. Requiring overall success intentionally waits for Pages as well; if Pages is to be independent, a narrowly scoped explicit handoff after `release` or manual dispatch against independently verified successful upstream jobs is clearer. An in-workflow `needs: [check, release]` job can reuse current-run artifact/outputs, but it couples store approval/retries to release runs and ties privileged workflow configuration to the source run's ref. Keep store secrets only in the actual per-store publish job, with a fixed environment limited to the protected `testing` ref for the separate workflow. A solo maintainer needs a viable reviewer path before enabling prevent-self-review. — [release dependency graph](../../.github/workflows/release.yml#L104-L143), [workflow_run](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run), [required reviewers](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments#required-reviewers)
- Prefer a GitHub-hosted secret-free preflight and GitHub-hosted publish if the store supports it. If a local authenticated client is necessary, prefer the maintainer's manual local handoff of verified files; never attach the maintainer's ordinary logged-in machine as a public repository runner. If central automation truly needs self-hosting, use a separate trusted private control repository or runner group actually restricted to trusted workflows where supported, disposable clean runner/VM, no personal account/session or unrelated files, minimum network access; make cross-repo access read-only to the producer and keep third-party caches and build code out of the publisher. Labels and environment approvals alone do not make a runner a security boundary. — [self-hosted hardening and JIT caveat](https://docs.github.com/en/actions/reference/security/secure-use#hardening-for-self-hosted-runners), [environments and self-hosting](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments#environment-secrets)

### Gaps
- Current tag/branch protection, previous approval practices, and availability of restricted runner groups or an isolated publisher were not established. Confirm before granting any store credentials. Decide explicitly whether a failed Pages deployment should block stores and whether to support upstream dispatch as a source on day one. — [current workflows](../../.github/workflows/release.yml), [GitHub environment options](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)

## 3. How should retries and downgrade prevention work, and what is the smallest scenario?

### Takeaway
Store state requires its own freshness/idempotency gate, independent of GitHub tag validation. First demonstrate one existing stable run → verified one-store payload → maintainer review. Enable a write path only when the selected store can be updated and read back safely.

### Cited Findings
- Current regression evidence covers a **new dispatch** of the same tag: notes survived and `SHA256SUMS` was identical. This is distinct from re-running all jobs on the same run ID (fixed v4 artifact name, no `overwrite`); a repeated upload can conflict with an existing name, so verify behavior rather than assume the observed dispatch result covers it. GitHub reruns preserve event ref/SHA and triggering actor privileges; partial reruns preserve outputs of jobs that were not rerun. Using a literal `refs/tags/...` checkout can still re-resolve a moved tag. If naming artifacts per attempt, keep the explicit successful build artifact ID across partial reruns; if overwriting, an old approved ID should fail closed rather than resolving its replacement. — [original rerun evidence](../../specs/006-release-publishing/research.md#L323-L335), [current producer YAML](../../.github/workflows/release.yml#L74-L127), [rerun semantics](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs), [artifact-v4 overwrite behavior](https://github.com/actions/upload-artifact/tree/v4#overwriting-an-artifact)
- Current release grouping is by **tag**, so it does not order different versions targeting the same item. The final-version tag check is an early snapshot, with no external store read, and it is not rerun by `publish`. `gh release upload --clobber` deletes an old asset before uploading a replacement and may lose it on failure, despite the “never deletes” source comment. An expired artifact or missing/mismatched published asset must not silently redirect publishing to a different run or tag. — [concurrency and publish gate](../../.github/workflows/release.yml#L17-L24), [final tag comparison](../../tools/release/tags.ts#L90-L102), [publish CLI](../../tools/release/cli.ts#L54-L63), [upload invocation](../../tools/release/publish.ts#L39-L52), [gh CLI deletion semantics](https://cli.github.com/manual/gh_release_upload)
- GitHub concurrency can serialize jobs per group, with `cancel-in-progress: false` preserving the active job, but the default queue replaces an existing pending job; ordering is not guaranteed by dispatch time and says nothing about SemVer. Current docs also describe opt-in `queue: max`; neither mode replaces a version check. — [GitHub concurrency rules](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#concurrency)

### Inferences
- Give each store/item its own concurrency group across **all** input versions, and separate status/retries per store. Just before mutation, inside the serialized approved publisher, re-read the tag commit, release state and the chosen source identity, veto any draft/prerelease (both SemVer and GitHub flag), and apply the same freshness policy to automatic/manual paths. Suggested first policy: candidate must still be the greatest canonical final release tag and be the checked published release; a newer tag can deliberately hold back the older candidate while the new release is incomplete. Separately compare to the actual store version or a reconciled per-store verified version/digest record, since GitHub knows nothing about out-of-band/manual store updates. Lower version → reject; equal version with proven same payload/state → no-op; equal unknown or differing state, or unknown current version → stop for reconciliation. No generic force/rollback switch. After a write or ambiguous failure, read back archive/version/notes state where possible before recording success or retrying; use a per-store retry rather than replaying another store's success. Keep identity/run/artifact/hash and outcome in a non-secret job summary, with durable verified state where the store cannot supply it. GitHub concurrency cannot serialize against external manual edits; coordinate those or use a conditional mutation if supported. — [tag semantics](../../tools/release/tags.ts#L82-L101), [SemVer comparator](../../tools/release/semver.ts#L56-L65), [existing manual store procedures](../../docs/releasing.md#L82-L113), [GitHub concurrency rules](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#concurrency)
- **Smallest representative scenario:** manually select `v0.2.0` / run `40677211348` and one host (e.g. KDE) in a read-only preparation job on `testing`. Fetch that run's `release-assets`, verify provenance and checksum manifest, show fixed existing item, tag/commit, run/artifact ID, exact archive and changelog names/hashes and current eligibility for review. Produce the verified payload for the existing manual update, with no store mutation, no rebuild and no store credentials. Acceptance: expected files match the published `v0.2.0` bytes; repeating preparation yields the same hashes; failed/wrong source run, mismatched tag, draft/prerelease, missing/expired artifact, checksum alteration and stale candidate are rejected. If that historical run's artifact expires, select a new checked final run explicitly. First **live** scenario after maintainer approval and store-specific feasibility: update one already-existing item with the archive and required version/change note, read it back, rerun to confirm no-op, then expand to the other store and optional listing updates. Gallery uploads remain manual under the constitution. — [candidate run](https://api.github.com/repos/Alamion/heroes_III_ts/actions/runs/40677211348), [live checksum baseline](https://github.com/Alamion/heroes_III_ts/releases/download/v0.2.0/SHA256SUMS), [existing store paths](../../docs/releasing.md#L82-L113), [gallery rule](../../.specify/memory/constitution.md#L76-L85)

### Gaps
- Before implementing writes: the store researchers/maintainer must establish which store is first, a supported publisher and credential/approval path, whether actual release version and uploaded payload can be read back, and how to reconcile partial failures and external manual edits. Confirm whether freshness should block on a newer tag awaiting publication, or on a newer verified published release only. Decide retention and recovery contract: missing Actions artifacts should fail clearly for the first scenario; later fallback to exact GitHub Release assets needs an independent trusted run-to-release identity plus verification, not `latest` or regeneration. — [existing manual process](../../docs/releasing.md#L73-L113), [artifact retention](https://github.com/actions/upload-artifact/tree/v4#retention-period), [observed mutable release](https://api.github.com/repos/Alamion/heroes_III_ts/releases/tags/v0.2.0)
